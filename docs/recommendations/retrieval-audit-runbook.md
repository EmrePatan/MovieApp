# Running the recommendation retrieval audit

This tool is **offline and read-only**. It does not access a database, call the API, modify user data or change recommendation behavior.

## Run synthetic diagnostics

From the MovieApp repository root on the research branch:

```bash
python3 tools/recommendation_retrieval_audit.py --self-test
python3 tools/recommendation_retrieval_audit.py \
  --input tools/fixtures/recommendation_retrieval_synthetic.json \
  --budget 3 --top-k 3
```

The fixture is **synthetic**, not staging evidence. A self-test passing establishes only internal consistency of the diagnostic, not recommendation quality.

## Input requirements for staging export

Provide a JSON object with `profiles` and `candidates` arrays, following the fixture. Export only anonymized IDs and numeric/ID metadata needed for evaluation. Do **not** export names, email addresses, reviews, search terms or raw activity history. Use a staging snapshot, not production.

The exporter must explicitly calculate `eligible` using the app's release-date, vote-count and other content eligibility rules. It must also include the user's complete existing exclusion IDs (watched, rated, favorite, watchlist, followed, etc.). Without these, diagnostic numbers are invalid.

For `keyword_weights`, export the normalized values generated by the existing application preference builder, including the same catalog-frequency configuration. Do not substitute raw keyword counts and claim equivalence.

## Interpretation limits

- This script isolates hard genre filtering and vote-first truncation. The real repository also uses type budgets, genre stratification, backfilling and hydration. **This is not an exact production baseline.**
- The alternative 70/30 split is **candidate retrieval allocation**, not 70/30 final recommendation output. Final ranking and reranking must be evaluated separately.
- `top_keyword_matches_retrieved_*` measures whether the highest keyword-overlap candidates appear in each candidate pool, not relevance, user satisfaction, Recall@10 or NDCG@10.
- Do not use the same users or events for profile construction and evaluation labels; temporal leakage will invalidate results.
- When profile keyword weights are absent, keyword opportunity counts will be zero; this is a missing-data condition, not proof of quality.
- Mixed movie/TV results require a follow-up harness that exactly reproduces type-specific budgets and production candidate selection.

## Before accepting any quality claim

1. Verify actual C# candidate selection equivalence on a small, controlled staging corpus.
2. Measure genre and keyword coverage, including Drama prevalence.
3. Run temporal holdout NDCG@10 / Recall@10 with user-level aggregation.
4. Benchmark PostgreSQL p50/p95 latency, round trips and query plans on staging.
5. Verify exclusions, cold start, response contract and diversity invariants.
6. Keep any future algorithm behind a default-OFF feature flag until reviewed.

No benchmark execution is implied by the existence of this document or its fixture.
